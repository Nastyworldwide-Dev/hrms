# PWA forms and requests — deep audit supplement

Audited HEAD `3ead59787`, 8 September 2026. No application or database changes. This extends the [reported-symptom audit](2026-09-08-attendance-ot-audit.md) and complements the [notification audit](2026-09-08-notifications-deep.md).

## PWA1 — High: five request types cannot show their approval actions

`frontend/src/components/RequestActionSheet.vue:113` requires `hasPermission('approval')` for the decision buttons. At line 398 only Leave Application translates that action into a writable decision-field check. Expense Claim, Shift Request, Attendance Request, OT Request and Replacement Leave Claim instead look up `permissions.approval`.

Standard Frappe permission results have no such key. Read-only local inspection confirmed no custom Permission Type named approval for these six DocTypes, and the native permission-right list contains only standard rights. The actual Vue function returns false for all five affected types even with every standard right and both decision fields permitted. Leave Application is the passing control. Custom permission configuration on another site must be checked before claiming identical reachability there.

**Impact:** an authorized reviewer can open a request but never receive Approve/Reject. A detail-page Review button alone cannot repair its action sheet. Ordinary Submit is not an equivalent fix because the server requires a valid decision and controls its consequences.

**Correction:** expose a consistent server decision capability to both PWA entry points and the sheet, retaining workflow handling, self-approval restrictions, company scope and the existing atomic `decide` endpoint. Do not grant general write/submit rights to make a button appear. Exercise actual buttons for all six types as employee, routed manager and HR, plus forbidden/self/cross-company cases.

**History:** `cf513efad0`, 6 September, introduced the present permission branch. Hafiz's 8 September detail review entry (`4490f444f2`) still leads to it; preserve the useful new entry and fix the shared gate.

## PWA2 — High when a routed reviewer lacks decision-field rights: PWA disagrees with the server

`FormView.vue:733–743` requires the status field in `permittedWriteFields` before showing Review. The server's `approval.py:230–238,278–291` explicitly admits a routed approver even without ordinary submit/field rights. Expense Claim's `approval_status` and Leave Application's `status` are permission level 1 in their actual JSON. An Employee-only named approver can satisfy routing without those field rights.

The actual `canReview` declaration returns false for that Expense Claim configuration. This establishes a capability mismatch; it does not claim a full authenticated approval completed, since downstream controller validations also run. An earlier synthetic OT example was rejected during review: stock OT status is permission level 0, so that specific field-permission combination was not established. The probe now uses Expense Claim's actual restriction.

**Correction:** use the same authorized decision contract throughout Desk and PWA. Review `can_decide` itself against every gate in `decide`: its submit-right branch currently omits the additional read/decision-field checks performed by the write endpoint. A UI capability must be conservative and accurate; the write endpoint remains authoritative.

## PWA3 — Medium: Back discards a new form without its promised confirmation

`FormView.vue:482` asks for confirmation only when `isFormDirty` is true. The deep form watcher at line 520 immediately returns when there is no `props.id`. New requests therefore never arm that protection. Executing the actual callback after a new-form edit leaves the flag false. Existing-document edit tracking still works.

**Correction:** distinguish initial defaults from subsequent user edits for new and saved forms. Protect supported navigation exits consistently, including browser/device Back where applicable. Test changing, reverting, saving and leaving a new request. The recently added discard dialog is worth preserving; its state source is incomplete.

## PWA4 — Medium: failed attachment batches are treated as complete

`FormView.vue:591–605` awaits `Promise.allSettled` without checking any outcome. Its create-success callback at line 612 then navigates to the detail screen even after rejected uploads. Actual production-function execution confirms the batch resolves normally when every upload rejects.

Individual `FileAttachment.upload` calls can show an error toast (`frontend/src/composables/index.js:26`), so this is **not** a wholly silent error. The defect is losing the pending upload/retry workflow while reporting successful request creation. The new native Helpdesk `TicketNew` has the same family of failure, reproduced in the first audit.

**Correction:** retain failed files with per-file retry, show that the document exists but its attachments are incomplete, and navigate only when that outcome is handled. Never create a second request just to retry attachments. Preserve successful files and enforce attachment ownership/access on the server. Cover mixed success, complete failure and retry without duplicate documents.

## PWA5 — Medium: a slower OT response overwrites the currently selected day's hours

`OTRequestForm.vue:183–212` fetches a day summary on date change and unconditionally writes the response into the current form. Installed `frappe-ui/src/resources/resources.js` supplies no request-generation guard for this usage.

The probe runs the actual installed resource and Vue callback. Request 3 September, then select 4 September. The 4 September response arrives first with 4h; the earlier response then writes 1.5h. The form now contains **4 September with 1.5h**. Server validation can reject an excessive value, but a lower stale claim can pass the cap; no payout or authenticated save was attempted.

**Correction:** apply results only to the employee/date/request generation that initiated them. Clear stale claim values immediately, show loading/failure explicitly, and prevent save while the current date's calculation is unresolved. Protect both summary text and the saved model; merely hiding the text cannot fix the submitted amount.

## PWA6 — High: the notification account-switch defect also affects personal request caches

The family hunt found fixed user-independent keys in `frontend/src/data/leaves.js`, `claims.js`, `attendance.js`, `overtime.js` and `team.js`. Installed `frappe-ui/src/resources/resources.js:194–202` hydrates stored data while a fresh request is loading or has not completed. `session.js:40–48` resets user/employee memory but does not purge those persisted resources.

The added probe executes the actual `myOTRequests`, parameter builder, transform and installed resource. With account B's employee parameters and its request still loading, the resource restores account A's synthetic OT row. This is the same privacy defect as notification N01, reproduced on a second resource implementation. It does not depend on successfully logging in while completely offline. Authenticated browser display timing still needs integration verification.

**Correction:** inventory and scope all personal cached resources by authenticated user and site, invalidate obsolete unscoped entries, and clear session-owned storage on logout. Preserve useful same-user offline behavior. Leave/expense/team keys are confirmed sibling paths with the same persistence mechanism; their full rendered account-switch flows were not separately replayed. Do not patch only the notification key or turn frontend cache filtering into a replacement for server authorization.

## Rechecked coverage and remaining risks

- The original GPS stale-coordinate, client/server distance-policy mismatch, invisible zero claim and inconsistent OT readers remain reproduced in the first audit. Their fixes need shared contracts, not individual text changes.
- `RequestPanel.vue:119` merges failed resources as empty arrays. Its template exposes no resource failure state. This previously reported defect remains: a missing request can look like an empty queue. Preserve the new approver-tab visibility and fallback clamp while adding partial-failure feedback.
- Request history at `RequestPanel.vue:108` includes leave, expense and shift only. Its comment says OT/Attendance/RL have no decision fields, which is stale against current metadata and `DECIDE_THEN_SUBMIT`. Whether users require those histories in this panel needs a product decision; the coverage omission is source-confirmed.
- Read-only local `get_doctype_fields` checks as an ordinary Employee found no unreadable editable Link targets across ten supported forms. This checks metadata, not rendered pickers or every possible role. Do not claim Hafiz's earlier dead-link-control work is still universally broken.
- Browser inspection reached the local login page. No authenticated form, service-worker update, offline recovery or physical GPS test was completed. Local served assets and production deployment may differ from audited source.
- The end-to-end suite contains obsolete routes, request seeding without CSRF, and skip-on-seed-failure behavior. Its approval path does not prove that the real Approve button is usable. See the [evidence report](2026-09-08-360-evidence.md).
