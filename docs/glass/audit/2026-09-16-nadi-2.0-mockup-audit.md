# Nadi 2.0 mockup — UI/UX audit

16 September 2026 · branch `nz-glass` · artifact `045d8f25` version `1789579513-4ea1`
(1020 lines, read in full). Reviewed as Senior Product Designer + Frontend Engineer.
Scope: the PWA mockup only — not Desk, not backend, not doctypes.

**Every number below was measured, not estimated.** Instruments:

| Instrument | What it produced |
|---|---|
| Playwright + chromium, artifact rendered at 500×1000 (app = 390×844) | tap targets, per-screen content height, tab order, focus-ring clipping, text-scaling behaviour, computed spacing |
| axe-core 4.x over `#app`, 11 screens × 2 themes + 4 sheets open | automated violations |

Verdict: **the structure and language are strong; the mockup is not yet buildable
as drawn.** 9 Critical, 11 Important, 8 Minor. The Criticals are concentrated in
two places: keyboard/screen-reader behaviour, and a silent fork of the design
tokens that `yarn gates` would reject.

## 0. What is genuinely good (keep these, do not re-litigate)

Stated first so the fix list is not read as a rejection.

- **The IA thesis is right.** "A row that can act, acts" removes a whole class of
  navigate-then-act round trips. Home's "Needs you" rows carry their verb.
- **Requests owning everything request-shaped** (balances, waiting, decided, claims)
  is a real simplification over the shipped Leaves/Expenses/OT split.
- **Role-widening visibility** — colleague sees *that*, approver sees *why* — is a
  clean, defensible rule, implemented consistently in both the team list and the
  day sheet.
- **Icon-only buttons carry real labels.** `aria-label="4 requests waiting for your
  decision"` is better copy than most shipped apps manage. Calendar arrows labelled
  "August"/"October", not "Previous"/"Next". Credit.
- **`prefers-reduced-motion`, `prefers-reduced-transparency` and `prefers-contrast`
  are all handled**, with glass degrading to a solid fill. Most mockups skip this.
- **Touch targets pass everywhere.** Measured every interactive element on all 11
  screens: **zero under 44×44** inside the app. `--tap:2.75rem` is applied with
  discipline.
- **Desktop sheets measure exactly 480px centred**, matching plan §2.4. Side nav
  216px, tab bar correctly `display:none` at desktop.
- **Employee Advance is absent** — no route, tile, label or link. The standing
  ruling (plan §2.7) is honoured.
- **The Friday prayer-break detail is right.** Day 11 carries "Prayer break 1h 45m"
  = 105 minutes, and 11 Sep 2026 *is* a Friday. Someone checked.

## 1. Global atomic UI — typography and colour

### C1 · CRITICAL · The mockup silently forks the design tokens

Plan §2.1 locks `design/tokens.json` and says "token churn is out of scope".
The mockup redefines eleven of them. Light theme:

| Token | `design/tokens.json` | Mockup | Consequence |
|---|---|---|---|
| `ink2` | `#545C68` | `#3D444E` | darker |
| `ink3` | `#878F9B` | `#5A626D` | see C2 |
| `accent-ink` | `#3F5C00` | `#3A5500` | drift |
| `danger-ink` | `#DC2626` | `#A01B14` | drift |
| `warn-ink` | `#B45309` | `#6B4404` | drift |
| `leave-ink` | `#5D46C2` | `#46309F` | drift |
| `success-ink` | `#007764` | `#00503E` | drift |
| `rest` | `#B6BDC9` | `#9AA3B0` | drift |
| `glass-fill` | `rgba(255,255,255,.56)` | `.58` | drift |
| `radius-panel` | `20px` | `17px` (reuses `r-card`) | panels wrong radius |
| `radius-tabbar` | `22px` | `23px` (`2.375rem − .9375rem`) | drift |
| `content-column-lg` | `720px` | `760px` | contradicts open item O2 |
| `pad-row` | `11.5px 15px` | `9px 14px` | every list row |
| `pad-panel` | `14px 13px` | `14px` | every panel |
| focus ring | `0 0 0 2px ink, 0 0 0 5px brand` | `0 0 0 2px bg, 0 0 0 4px ink` | no brand, 1px thinner |

None of these is *worse* in isolation — several are darker, i.e. higher contrast.
That is exactly the problem: they are unexplained improvements to a locked system.
Two outcomes, both bad: either `design/gates/tokens.mjs` + `contrast.mjs` fail the
build, or the token file changes and plan §2.1/§7 is breached.

**Fix:** the mockup must consume `design/tokens.json` values verbatim. If a token
is genuinely wrong, raise it as a separate token-change decision with its own
approval — do not smuggle it in through a layout mockup.

### C2 · CRITICAL · `ink3` is used for text; the token says it must not be

`tokens.json` on `ink3`: *"Non-text only: chevrons, dividers, disabled. Light value
deliberately raised from #8A929E to clear 3:1. Never apply opacity multipliers."*

The mockup lowers it to `#5A626D` and then uses it as a **status colour**: the
"Expenses · Not sent yet" row marker is `style="background:var(--ink3)"`, and
`.grab` and `.chev` also ride it. Lowering a token so a forbidden use becomes legal
is backwards.

**Fix:** keep `ink3` at `#878F9B`, non-text only. Give "Not sent yet" its own
neutral state token (the repo already has `GStatusChip` variant `muted`,
measured 4.56/4.58).

### C3 · SERIOUS · Calendar state dots fail SC 1.4.11, and the CSS comment
### claims otherwise

Measured against the `.day` surface `#F8F9FB`, threshold 3:1:

| Mark | Ratio | |
|---|---|---|
| `m-ot` (brand lime) | **1.12** | FAIL |
| `m-pres` (success) | **1.54** | FAIL |
| `m-tv` (travel) | **2.03** | FAIL |
| `m-half` (warn) | **2.04** | FAIL |
| `m-rest` | **2.42** | FAIL |
| `m-tr` (train) | **2.51** | FAIL |
| `m-abs` (danger) | **2.63** | FAIL |
| `m-lv` (leave) | 4.14 | pass |

The source comment argues the dark ring rescues this. It does not. The ring is
**identical on all eight marks**, so it makes the dot *visible* but cannot make one
state distinguishable from another. Seven of eight states are separated by hue
alone, at 7px, which also fails **SC 1.4.1 Use of Colour** — and the legend proves
it, because every legend entry differs only by dot colour.

**Fix:** give each state a distinct *shape* or glyph (filled circle / ring /
half-filled / cross / bar), not a distinct hue. Shape survives colour-blindness,
greyscale printing and a 7px render. Keep hue as reinforcement.

### C4 · SERIOUS · axe: 11 contrast violations on the calendar, from `opacity`

`axe` reports `color-contrast` ×11 on `.day.out` — days outside the current range,
dimmed with `opacity:.5`. `tokens.json` says explicitly: *"Never apply opacity
multipliers (spec 2.5)."* The mockup does exactly that.

**Fix:** a real dimmed-day token, not an opacity multiplier.

### Type scale, line height, measure

Scale is a clean 6-step ramp (36 / 24 / 21 / 15 / 13 / 11 px at root 16), all in
rem. Line heights: display 1.0, title 1.15, body 1.3–1.5. Reasonable.

**I1 · IMPORTANT · Desktop line length is 106 characters at 13px.**
Measured on the Home announcement paragraph: content column 760px, computed font
13px, **106 characters per line**. The readable range is 45–75. Two compounding
problems — the line is 40% too long *and* the body copy is 13px, which is a caption
size being asked to carry paragraph text.

**Fix:** announcement/paragraph text to 15–16px; cap prose blocks at `65ch`
regardless of the column width. The 760px column also contradicts the 720px token
(open item O2) — pick one, and let O2 be decided on the number, not inherited from
a mockup.

**M1 · MINOR** · `.display` uses `line-height:1` at 36px. Fine for the clock
figure; will clip descenders if it ever renders text with a `g` or `y`.

### No AI artefacts or visual noise found

Iconography is a consistent 24-box stroke set at 1.8–2.2 weight, `currentColor`,
`aria-hidden`. No mismatched grids, no stray gradients, no fake shadows. This part
is clean.

## 2. Grid, alignment, white space

### I2 · IMPORTANT · There is no 4px/8px grid — in the mockup or the design system

Measured computed spacing across 13 component classes. Off the 4px grid:

`card` padding 14 · `panel` padding 14 · `row` padding 9/14, gap 11 · `tile` 13 ·
`sheet` 10/15/14 · `sect` margins 13/7 · `pill` 3.5 · `legend` gap 5 ·
`iconbtn` padding 1/6 · `title` margin 10 · `input`/`switch` 14 · `ghost` 14

That is most of the system. **But `tokens.json` is itself off-grid by design** —
`screen-gutter 15px`, `stack-sm 9px`, `stack-md 13px`, `pad-row 11.5px 15px`.

So the honest finding is not "the mockup breaks the grid". It is:

1. This design system does not use a 4/8px grid and never claimed to. Asking for
   grid adherence is asking to rebuild the spacing scale — a token change, out of
   scope per plan §2.1.
2. The mockup is inconsistent with **the real contract**: rows are `9px 14px`
   where the token says `11.5px 15px`; panels are `14px` where the token says
   `14px 13px`.

**Recommendation:** drop the 8px-grid framing. The defensible rule is *conform to
the token spacing ladder*, which is enforceable by `design/gates/usage.mjs`. If a
true 4px grid is wanted, that is a separate, costed decision about `tokens.json`.

### Padding, hierarchy, dead space — assessed

- Vertical rhythm is coherent: `sect` 13px above / 7px below reads as a clear
  group separator.
- **M2 · MINOR** · `.iconbtn` has `padding:1px 6px` — an artefact of `display:grid;
  place-items:center` on a fixed 44px box. Harmless, but it is noise in the
  computed styles and will confuse the next person diffing them.
- **M3 · MINOR** · Home's greeting block ("Tuesday, 16 September" + "Good morning,
  Nabil") occupies ~70px above the fold to convey nothing actionable. See I8.
- No dead space found at phone width. At desktop, the 760px column inside an
  1180px app leaves a large empty right margin with no use — see I7.

## 3. Component and element states — the frontend contract

### C5 · CRITICAL · The mockup defines almost no states

Searched the entire stylesheet. Present: `:active` (on `.cta` only), `:focus-visible`
(one global rule). **Absent: every `:hover`, every `:disabled`, every error state,
every loading state, every selected state on rows.**

The plan mandates a desktop shell at ≥1024px. On desktop, hover is not decoration —
it is the primary affordance that tells a pointer user a row is interactive. And
every button in this app sends something to an approver; without a pending/disabled
state users will double-submit.

**This is the state matrix the implementation needs.** Written against the real
tokens so it is buildable as-is:

| Component | Rest | Hover (pointer only) | Focus-visible | Active | Disabled | Loading / pending |
|---|---|---|---|---|---|---|
| `.cta` primary | brand→brand-2 gradient, `shadow.action` | brightness 1.06, lift shadow +2px | `shadow.focus-ring` (2px ink + 3px brand) | `scale(.985)`, inner shadow deepens | `--track` fill, `--ink3` text, `cursor:not-allowed`, `aria-disabled` | label→spinner-free "Sending…", `aria-busy`, pointer-events none |
| `.ghost` | transparent, `--hair` border | `--well` fill | `shadow.focus-ring` | `--well` darkened | 40% text, border `--hair` | as above |
| `.act-inline` (row verb) | `--surface`, `--hair` border | `--well` fill, border `--ink3` | `shadow.focus-ring-inset` (see C7) | scale .98 | `--track`, `--ink3` | label→"…" , width locked to avoid reflow |
| `.row` / `.rowbtn` | transparent | `--well` background | `shadow.focus-ring-inset` | `--well` +4% | n/a | `GSkeleton` row |
| `.input` / `select` / `textarea` | `--surface`, `--hair` | border `--ink3` | `shadow.focus-ring`, border `--accent-ink` | — | `--track` fill, `--ink3` text | — |
| `.input` **invalid** | — | — | — | — | — | border `--danger-ink` 1.5px, `aria-invalid="true"`, message below in `--danger-ink` linked by `aria-describedby` |
| `.tabs button` | `--ink2` | `--well` pill behind icon | `shadow.focus-ring` | — | — | — |
| `.side button` | `--ink2` | `--well` | `shadow.focus-ring` | — | — | — |
| `.tile` | `--surface` | `--well`, border `--ink3` | `shadow.focus-ring` | scale .98 | — | — |
| `.cal .day` | `--surface` | `--well` | `shadow.focus-ring` | — | `.out` → dimmed **token**, not opacity | `GSkeleton` grid |
| `.track-sw` switch | `--track` | track +6% | `shadow.focus-ring` | knob scale 1.1 | 40%, `aria-disabled` | — |
| `.seg button` | transparent | `--well` | `shadow.focus-ring` | — | — | — |

Two rules for all of it:

- Hover must be `@media (hover:hover) and (pointer:fine)` — otherwise mobile
  browsers leave a sticky hover after tap.
- Disabled must use `aria-disabled="true"` plus a click guard, **not** the
  `disabled` attribute, or the control drops out of the tab order and a screen
  reader user never learns why it cannot be used.

### Touch targets — PASS

Measured all 11 screens: every interactive element ≥44×44. Calendar days compute
to 48×48 at 390px width. Rows, inline actions, icon buttons, switch, segmented
options all exactly 44. **No action needed.** (The mockup-chrome toolbar buttons
are 32px, but that is the demo harness, not the app.)

## 4. Information architecture and navigation

### C6 · CRITICAL · `aria-selected` on plain buttons — axe critical, on every screen

10 elements. axe reports `aria-allowed-attr` **critical ×5 on all 11 screens and
all 4 sheets**. The tab bar and side nav set `aria-selected` on `<button>` with no
`role="tab"` and no `role="tablist"` parent. `aria-selected` is invalid there, so
assistive tech is told nothing about which destination is current.

This also **adds to existing debt**: `design/a11y-baseline.json` already carries
`aria-allowed-attr` on 5 screens, and `design/gates/a11y.mjs` fails on any *new*
serious/critical finding. This mockup, built as drawn, fails the gate.

**Fix:** navigation is not a tablist. Use `aria-current="page"` on the active
destination and drop `aria-selected`. For the Help segmented control, keep
`role="tab"` but complete it — see I5.

### I3 · IMPORTANT · Sub-pages have no heading

`show()` hides the screen's `<h1>` on every non-tab page and puts the name in a
`<span class="subttl">` in the header. The accessible *name* of the section
survives via `aria-labelledby` (referencing a hidden element is permitted), but
the page is left with **no heading element at all**. Screen-reader users navigate
by heading; on Approvals, Help, Announcements, Notifications, Profile and the leave
form there is nothing to navigate to.

**Fix:** keep one visible `<h1>` per screen, or make the header's `subttl` the
`<h1>`. Do not render a page with zero headings.

### I4 · IMPORTANT · The tab set answers a question the plan lists as OPEN

| | Home | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| Mockup | Home | Calendar | Requests | **Score** | More |
| Shipped (`navItems.js`) | Home | Attendance | Leaves | Expenses | More |
| Plan | — | — | — | — | — (O4: **OPEN**) |

The mockup presents a resolved answer to an unresolved decision. Worse, three of
its choices collide with facts already on record:

- **"Score" as a permanent tab.** KPI currently sits under More. Putting a
  performance grade in the bottom bar means every employee sees their score every
  time they open the app. That is an organisational decision, not a layout one.
  It needs an explicit ruling before it is drawn as settled.
- **"Payslips" in More.** `navItems.js` states: *"There is no Pay screen in this
  app — no salary-slip route exists, and building one is a new feature (§1, out of
  scope)."* Payroll also stays out of Verifica by standing ruling. This row cannot
  ship.
- **Help buried under More, split HR/IT.** The owner ruled on 15 Sep — one day
  before this mockup — that Issues + Helpdesk get **one** entry, in the slot Issues
  held. The mockup contradicts a one-day-old ruling.

### I5 · IMPORTANT · Out-of-scope domains are drawn as if they exist

Plan §7 excludes new domains: **travel, assets, training, events**. Also excluded:
Announcements ("committed launch scope, still unbuilt — a feature, not a 2.0 slice").

The mockup ships: "Training", "Things you hold" (assets) and "Public holidays" in
More; "Work trip" (travel) in the New-request sheet; and **Announcements as the
lead block on Home plus its own screen**.

**Fix:** mark every one of these as *proposed, not in 2.0* in the mockup itself
(a visible "not in this release" treatment), or remove them. A mockup that shows
six things the release will not contain cannot be used as the design contract for
that release.

### Wayfinding — assessed

- Back behaviour is correct: `stack` resets on tab change, `back()` falls back to
  Home. Requests → leave form → back returns to Requests.
- Header rule (logo on tabs, place-name + back on sub-pages) is sound and
  consistently applied.
- **M4 · MINOR** · On desktop the logo renders **twice** — in the side nav and in
  the header. The mockup's own stated rule is "No word appears twice." Drop the
  header logo at `lg:`.

### Scanning priority — critique

Home, in eye order: greeting → clock figure (36px) → "Needs you" → announcement.

**I8 · IMPORTANT** · The largest type on the screen is "Good morning, Nabil"
(21px bold) and it carries zero information. The first *actionable* thing is the
clock state. For a shift worker opening this app at 08:30, the priority is:
(1) am I clocked in, (2) what needs me, (3) news.

**Fix:** demote the greeting to the 13px label line, promote the clock card, and
let "Needs you" sit directly beneath it. Recover ~40px above the fold at the same
time.

## 5. Transition and interaction logic

### Predicted behaviour for each primary action — and the recommendation

| Action | Mockup does | Should do | Why |
|---|---|---|---|
| **Clock out** (Home CTA) | toggles state + toast | **inline, optimistic** — card updates immediately, toast confirms, silent retry on failure | Highest-frequency action in the app. A modal here is friction; a page load is worse. |
| **Fix** (a broken day) | opens `sheet-fix` | **bottom sheet** ✓ correct | Short focused form, one decision, keeps the list context behind it. |
| **Claim** extra hours | fires a toast instantly | **inline expand → confirm** | It sends money-bearing data to an approver. One tap should not be irreversible. |
| **New request** | opens a 6-tile sheet | **sheet** ✓ correct | Disclosure of a type list is exactly what a sheet is for. |
| **Use** (leave balance row) | full screen navigation | **sheet on phone, 480px dialog on desktop** | Consistency: every other form in this app is a sheet. The leave form is the only one that navigates, which is why it needs its `<h1>` hidden (I3) — a symptom of the inconsistency. |
| **Approve / Decline** | instant toast | **optimistic + 5s Undo in the toast**; Decline keeps its reason sheet ✓ | Irreversible and visible to another person. |
| **Withdraw** | instant toast | **confirm** (`GConfirm` exists) | Destructive, no undo path drawn. |
| **Send** (unsent expense) | instant toast | inline, optimistic | Low risk, recoverable. |

**Seamless-UX recommendation, stated once:** this app should have exactly two
overlay types — a **bottom sheet on phone / 480px centred dialog on desktop** for
anything requiring input, and an **inline optimistic update + toast with Undo**
for anything that does not. No full-page navigations for forms, no confirm modals
except for destructive-and-irreversible. The mockup is ~80% there; the leave form
and the instant-fire Approve/Claim are the exceptions.

### C7 · CRITICAL · Sheets claim `aria-modal="true"` and behave nothing like modals

Measured with a sheet open:

| Check | Result |
|---|---|
| Focus moves into the sheet on open | **No** — stays on the trigger |
| Focus is trapped | **No** — tab stops 1–5 land on the tab bar *behind the scrim* |
| Escape closes it | **No** — "still open" |
| Background `inert` | **No** |
| Background `aria-hidden` | **No** |
| Background scroll locked | **No** — `overflow-y:auto` |
| Focus restored to trigger on close | **No** |

`aria-modal="true"` on a dialog that does none of this is a false statement to
assistive technology — worse than omitting it, because a screen reader will stop
announcing the background it can still reach.

**Fix:** the repo's `GModal` already solves this, including a documented
Ionic focus-trap workaround that must be preserved verbatim. Use it. Required
behaviour: move focus to the sheet (or its heading), trap Tab/Shift-Tab, close on
Escape, `inert` the background, lock body scroll, restore focus on close.

### C8 · CRITICAL · Closed sheets sit in the keyboard tab order

4 sheets, **12 focusable controls, all reachable while closed.** Measured tab walk
from Home with nothing open — stops 10 through 24:

```
10. Close          (sheet-day)      15. Change a shift  (sheet-new)
11. Time off       (sheet-new)      16. Work trip       (sheet-new)
12. Replacement day                 17-20. fx-time      (sheet-fix)
13. Expenses                        21. fx-why          (sheet-fix)
14. Fix a day                       22. Send            (sheet-fix)
                                    23. rj / 24. Send back (sheet-rej)
```

A keyboard or screen-reader user on Home tabs through fifteen invisible controls —
including two "Send" buttons — before reaching the mockup chrome. The sheets are
hidden with `transform:translateY(102%)`, which moves them off-screen but leaves
them focusable.

**Fix:** `display:none` (or `inert` + `visibility:hidden`) when closed. Animate
with `@starting-style` or toggle `inert` on the transition end.

### C9 · SERIOUS · Focus rings are clipped inside panels — and the token that
### fixes it already exists

Measured: the first row-button inside `.panel{overflow:hidden}` sits 1px from the
panel's top and left edge. The focus ring extends 4px outward. **It is clipped.**

`tokens.json` ships `shadow.focus-ring-inset`, described as: *"Inset variant of
focus-ring for controls inside an overflow:hidden panel (list rows), where…"* —
the design system anticipated this exact case and the mockup did not use it.

Second defect in the same rule: `:focus-visible{outline:none; box-shadow:…}`.
`box-shadow` is **stripped in Windows High Contrast / forced-colors mode**, so
those users get no focus indicator at all.

**Fix:** `shadow.focus-ring-inset` for controls inside panels, plus
`outline:2px solid transparent; outline-offset:2px` on every focusable element so
forced-colors mode substitutes a real outline.

### M5 · MINOR · No transition between tabs

`show()` toggles `display`. Acceptable on phone; abrupt on desktop where the whole
content column swaps instantly. A 120ms opacity/translate cross-fade, disabled
under `prefers-reduced-motion`, would cost ~6 lines.

## 6. Edge cases and accessibility

### C10 · CRITICAL · Empty, loading, error and offline states are essentially absent

The entire mockup contains **one** empty state: *"Everyone is working this day."*
There is no loading state, no error state, no offline state, anywhere.

This is not a theoretical gap:

- The repo ships **`GSkeleton` (18 uses)** and **`GEmptyState` (23 uses)**, with a
  documented copy rule: *"always say what to do, never 'no records found'"*.
- The 7 Sep audit already logged **F2 — "Home's Requests panel turns a failed fetch
  into 'Nothing here yet'"** and **F3 — "No offline handling in the PWA"**.

A mockup that omits error states is how F2 happened: with no error design, a failed
fetch silently renders the empty state, and the user is told they have no requests
when in fact the network failed. **This mockup would reproduce a defect already on
the record.**

**Required, per screen:** loading (skeleton mirroring the real block sizes),
empty (with an action, per the copy rule), error (with a retry), offline (PWA —
staff use this on outlet wifi). Minimum set to draw:

| Screen | Empty | Error | Offline |
|---|---|---|---|
| Home "Needs you" | "Nothing needs you today." | "Could not load. Retry" | cached + "Showing your last update" |
| Calendar | month with no records | retry | cached month |
| Requests (each of 3 groups) | per-group copy + action | retry | queue the action |
| Approvals | "Nothing waiting for you." | retry | read-only |
| Notifications | "You are up to date." | retry | cached |
| Help | "No questions open." + Ask HR | retry | queue |

Offline deserves a first-class answer: a clock-in taken with no signal must queue
and sync, not fail. That is a product decision this mockup should force, not skip.

### I6 · IMPORTANT · Truncation with no recovery

`.trunc` (`white-space:nowrap; text-overflow:ellipsis`) is applied to 14 rows —
request titles, help-thread subjects, approval summaries. There is no `title`
attribute, no tooltip, no expand, no wrap-on-focus. *"September pay looks short"*
is a support thread subject a user simply cannot finish reading.

**Fix:** two-line clamp (`-webkit-line-clamp:2`) for titles rather than a single
truncated line; reserve hard truncation for names and IDs, and give those a
`title`.

### I7 · IMPORTANT · The toast cannot wrap, and is the only feedback channel

`.toast{white-space:nowrap}` — measured, unchanged at 100/150/200% text. Every
confirmation in the app is a toast: "Claim sent to Hafiz", "Approved · Syamira
told", "Sent back with your reason". A real employee name plus a real error
message will run off a 390px screen.

Also: the toast is `role="status"` (polite). Correct for success, **wrong for
errors** — a failure must be `role="alert"` or it may never be announced.

**Fix:** allow wrapping with a max-width; two toast roles (status / alert);
add the Undo affordance from §5.

### C11 · CRITICAL · The 200% text switch does not test what it claims

The mockup advertises *"rem text scaling"* as WCAG evidence and ships a 100/150/200%
switch. Measured:

| Setting | Root font | `.app` width | Content height | Viewport height |
|---|---|---|---|---|
| 100% | 16px | **390px** | 615px | 777px |
| 150% | 24px | **585px** | 1069px | 720px |
| 200% | 32px | **780px** | 1422px | 626px |

`.app` is sized `24.375rem`, so raising the root font **inflates the device frame**
from 390px to 780px. The text never has to reflow — it is given twice the space.

That is the opposite of the test. SC 1.4.4 (Resize Text) and SC 1.4.10 (Reflow)
require content to remain usable when text doubles **inside a fixed viewport**.
On a real 390px phone, this layout has never been tested at 200%.

**Fix:** set `.app` width in `px` so the frame stays 390px while the text grows.
Then fix what breaks — and things will break: `.number` figures beside labels in
`.row`, the two-column `.tgrid`/`.pair` grids, `.pill` text, and the nowrap toast
are the likely casualties.

### Other accessibility findings

- **I9 · IMPORTANT** · The Help segmented control has `role="tablist"` and
  `role="tab"` but the panels have **no `role="tabpanel"`, no `aria-controls`, no
  roving `tabindex`, no arrow-key support**. Half an ARIA pattern is less usable
  than none. The repo's `GSegmented` implements it correctly — use it.
- **M6 · MINOR** · `.grab` (the sheet drag handle) is a `<div>` and is not
  operable. It reads as interactive. Either make it a real drag affordance or mark
  it `aria-hidden`.
- **M7 · MINOR** · Calendar days are labelled `aria-label="19 September"` with no
  state. A screen-reader user hears the date but not "worked", "time off" or
  "needs fixing" — the entire purpose of the grid. Append the state to the label.
- **M8 · MINOR** · `.cal .dow` weekday headers are `aria-hidden="true"`, so the
  grid has no column semantics. Use a real `<table>` or `role="grid"` with proper
  column headers.

### Colour is not the only carrier — mostly

Checked: pills pair colour with text ✓. Timeline dots pair with "In 08:55" text ✓.
The tab bar's selected state uses colour **plus** the `.tabdot` indicator ✓.
The failure is the calendar legend (C3), where colour is the only carrier.

## 7. Expansion — what the brief did not ask for

### Content and data realism

**I10 · IMPORTANT · Two date labels are wrong, and the app contradicts itself
on screen.**

| Shown | Truth (Python `calendar`) |
|---|---|
| Home: "**Tuesday**, 16 September" | 16 Sep 2026 is a **Wednesday** |
| Approvals: "**Mon 22** – **Tue 23** Sep" | 22 Sep is a **Tuesday**, 23 a **Wednesday** |

The calendar screen computes weekdays from real dates, so it renders "Your team ·
**Wed** 16 Sep" while Home says Tuesday — **the same build disagrees with itself**.
In an attendance product, where the whole value proposition is that the dates are
right, this is the detail a reviewer will fix on.

Verified correct: 1 Sep 2026 is a Tuesday and the Monday-first grid uses exactly
one leading blank ✓; rest days 6/12/13/19/20/26/27 match real weekends, with 5 Sep
correctly modelled as a *worked* rest day ✓; the Friday 105-minute prayer break on
day 11 ✓.

**M9 · MINOR** · The lead announcement is about Raya holidays in **March**, posted
"yesterday" (15 September), badged "New". Content that cannot be real undermines a
review. Use a plausible September announcement.

### Privacy — needs a ruling, not a design fix

**I11 · IMPORTANT** · `renderTeam()` shows the approver the *reason* for a
colleague's absence, including **"Medical leave"**, in a team list and in the day
sheet. Two questions this mockup should force, both outside a designer's authority:

1. Is disclosing medical-leave *type* to a line manager intended, and lawful under
   Malaysian PDPA? "Away" vs "Annual leave" vs "Medical leave" are three very
   different disclosures.
2. Medical leave is styled `p-no` — the **danger/red** treatment, the same one used
   for "Declined". Being ill is rendered as a failure state. Regardless of the
   privacy ruling, change the styling: sick leave is not an error.

### Screens and flows that do not exist yet

No sign-in · no session-expired · no permission-denied · no "you have no approver
assigned" · no leave-conflict warning (two people off the same day — the data model
clearly supports it, Syamira and Ria overlap on 17 Sep) · no push-permission prompt
· no PWA install prompt · no pull-to-refresh (`GPullRefresh` ships) · no search
anywhere · no pagination or "load more" on Requests, Notifications or Announcements
· no confirmation that a queued offline action eventually sent.

### Scroll budget — PASS, and better than both baselines

### Desktop

- **M10 · MINOR** · 1180px app, 216px side nav, 760px content column — leaving
  ~200px of unused right margin with no secondary content. On a desktop HR app the
  natural use is a persistent context rail (today's summary, pending count), or
  simply a wider column. Currently it is neither.
- The side nav's selected state is `--well` = `rgba(16,22,34,.05)` — a 5% tint.
  At a glance the current section is barely distinguishable. Pair it with a
  left accent bar or a stronger fill.
- **M11 · MINOR** · Desktop keeps the phone header's three icon buttons *and* the
  side nav's identity block, so the avatar appears twice.

## 8. Defensibility — how each fix survives review

The brief requires the mockup be defensible into real implementation. Mapping:

| Finding | Real component / file | Gate that proves it |
|---|---|---|
| C1, C2 token fork | `design/tokens.json` (unchanged) | `design/gates/tokens.mjs`, `usage.mjs` |
| C3, C4 marks & opacity | `GCalendar.vue` | `design/gates/contrast.mjs` (enforcing, exits non-zero) |
| C5 states | `GButton`, `GListRow`, `GInput`, `GSegmented` | `design/gates/coherence.mjs` + visual baselines |
| C6 aria-selected | `SideNav.vue`, `BottomTabs` | `design/gates/a11y.mjs` (fails on new critical) |
| C7, C8 sheet semantics | **`GModal.vue`** — already solves this, workaround must be preserved verbatim | `e2e/a11y.spec.js` |
| C9 focus ring | `shadow.focus-ring-inset` (already a token) | `a11y.mjs` |
| C10 empty/error/loading | **`GEmptyState`, `GSkeleton`** (already shipped, with copy rules) | unit tests per slice |
| C11 reflow at 200% | layout CSS | new e2e assertion at 390px × 200% |
| I4, I5 scope conflicts | `frontend/src/data/navItems.js` | owner decision, not a gate |
| I10 date labels | mockup copy | trivial |

**Nothing in the Critical list requires a new component.** Every one is either a
correction to the mockup or an instruction to use a Glass component that already
exists and already documents the correct behaviour. That is the strongest argument
for this mockup: its gaps are fillable from the system it is meant to describe.
