# Nadi checkable rulebook — alpha.12 (Apple HIG, fetched 26 Sep 2026)

Scope: iOS-style PWA "Nadi". Phone first (390 × 844 reference), desktop = wide window with sidebar.
Every rule: **ID** · checkable rule · verbatim Apple quote (page) or fallback · `measure:` one WebKit (Playwright `webkit`) check.
1 pt = 1 CSS px. "Nadi token" = our number, not Apple's. Existing alpha6 IDs are kept; new ones continue the series.
New families: **A** alignment · **O** offline/error · **D** loading · **K2x** keyboard · **F** performance · **Q** sorting.
Quotes are copied from `/tmp/a12/hig/<page>.txt` and were machine-checked (`grep -F`) against those files.

---

## 1. Type — sizes, weights, readability (T)

- **T1** Every rendered text node uses a size from the iOS default ramp {34, 28, 22, 20, 17, 16, 15, 13, 12, 11} px with its line height {41, 34, 28, 25, 22, 21, 20, 18, 16, 13}. — typography: "Consider using the built-in text styles. The system-defined text styles give you a convenient and consistent way to convey your information hierarchy through font size and weight." · measure: walk text nodes, `getComputedStyle(el).fontSize/lineHeight` pair ∈ ramp table (±0.5px).
- **T2** Font weight ∈ {400, 500, 600, 700}; no 100–300; 800/900 banned (Nadi choice, see §14). — typography: "prefer Regular, Medium, Semibold, or Bold font weights, and avoid Ultralight, Thin, and Light font weights, which can be difficult to see, especially when text is small." · measure: every text node `fontWeight` ∈ {400,500,600,700}.
- **T3** One UI typeface family (system stack `-apple-system`); a second face only for monospaced digits. — typography: "Minimize the number of typefaces you use, even in a highly customized interface." · measure: set of first-resolved `fontFamily` values across the page ≤ 2.
- **T4** No text below 11 px anywhere. — typography: "iOS, iPadOS | 17 pt | 11 pt" (default | minimum) · measure: min computed `fontSize` over visible text ≥ 11.
- **T5** Tracking follows SF: 17 px → −0.43 px (−0.026 em), 15 → −0.23, 13 → −0.08, 12 → 0, 11 → +0.06, 34 → +0.40. — typography: "17 | -26 | -0.43" · measure: `letterSpacing` per size within ±0.05px of the SF Pro table.
- **T6** No ALL-CAPS text runs longer than one word (no `text-transform: uppercase` on headers). — writing: "Choose a style for each UI element type and use it consistently throughout your app" · measure: no element with computed `textTransform: uppercase` and >1 word.
- **T7** Tab-root screens show a Large Title (34/41) that collapses to an inline title on scroll. — toolbars: "Use a large title to help people stay oriented as they navigate and scroll." · measure: at scrollY 0 title fontSize 34; after `scrollBy(0,200)` inline title visible, 17px.
- **T8** Screen titles < 15 characters and never "Nadi". — toolbars: "keep the title under 15 characters long so you leave enough room for other controls." · measure: `h1` / bar title `textContent.trim().length < 15` and ≠ app name.
- **T9** Body text default 17 px; reading text never smaller than 15 px (Subhead). — accessibility: "Use recommended defaults for custom type sizes." · measure: `.g-row` title fontSize = 17; paragraph text ≥ 15.
- **T10** Layout survives 200 % text: at root font-size ×2 nothing is clipped or overlaps and no horizontal scroll. — accessibility: "Ideally, give people the option to enlarge text by at least 200 percent" · fallback WCAG 2.2 SC 1.4.4 Resize Text · measure: set `html{font-size:200%}` (or `-webkit-text-size-adjust:200%`), assert `scrollWidth ≤ innerWidth` and no text node with `scrollWidth > clientWidth` unless it has an ellipsis-to-detail path.
- **T11** At large text, side-by-side label/value pairs stack instead of truncating. — typography: "consider using a stacked layout where text appears above secondary items." · measure: at 200 % text, row value `top` ≥ label `bottom` when `label.width + value.width > row.width`.
- **T12** Truncation only where a detail view shows the full text; ≥3-line text never uses tight leading (line-height ≥ 1.2× size). — typography: "If you need to display three or more lines of text, avoid tight leading even in areas where height is limited." · measure: any element with `text-overflow: ellipsis` sits inside a tappable row; blocks with ≥3 lines have `lineHeight/fontSize ≥ 1.2`.
- **T13** Paragraphs keep WCAG text-spacing overrides without loss (line-height 1.5, paragraph 2×, letter 0.12 em, word 0.16 em). — Apple gives no number · fallback WCAG 2.2 SC 1.4.12 Text Spacing · measure: inject the SC 1.4.12 bookmarklet CSS, assert no clipped text (`scrollHeight ≤ clientHeight` on fixed-height boxes).
- **T14** Reading-text line length ≤ 80 characters (content column ≤ 720 px on desktop). — layout: "restrict the width of text for optimal readability" · Apple gives no number · fallback WCAG 2.2 SC 1.4.8 (AAA, ≤80 chars) · measure: paragraph `clientWidth / (0.5 × fontSize)` ≤ 80; `.g-content` max-width ≤ 720.
- **T15** Hierarchy holds at every text size: the screen title stays the largest text and stays at the top. — typography: "Maintain a consistent information hierarchy regardless of the current font size." · measure: at 100 % and 200 %, title fontSize is the max on screen and its `top` is the min among content.

## 2. Colour and contrast (G)

- **G5** Exactly one control per screen has a brand-tinted background fill. — color: "Refrain from adding color to the background of multiple controls." · measure: count visible buttons whose `backgroundColor` ≈ brand (ΔE<5) ≤ 1 (≤2 allowed only if B1 exception logged).
- **G6** Brand colour never on non-interactive text (headings, labels, numbers). — color: "if you use your brand color to indicate that a borderless button is interactive, using the same or similar color to stylize noninteractive text is confusing." · measure: every text node with `color` ≈ brand is inside `a,button,[role=button],[role=tab]`.
- **G8** No state is shown by colour alone; each status chip has a word or a distinct icon shape. — accessibility: "Offer visual indicators, like distinct shapes or icons, in addition to color to help people perceive differences in function and changes in state." · measure: every `.g-tag`/status dot has non-empty `textContent` or `aria-label` + an SVG.
- **G9** Text contrast ≥ 4.5:1 up to 17 px; ≥ 3:1 at ≥ 18 px or bold (≥ 700) — in light AND dark. — accessibility: "Up to 17 pts | All | 4.5:1" and "18 pts | All | 3:1" and "All | Bold | 3:1" · measure: for each text node compute WCAG ratio of `color` vs nearest opaque ancestor background, both `colorScheme` emulations.
- **G9b** Small text on custom colours aims for 7:1; floor stays 4.5:1. — dark-mode: "For custom foreground and background colors, strive for a contrast ratio of 7:1, especially in small text." · measure: report (warn, not fail) text ≤13 px with ratio < 7.
- **G11** Non-text UI (field borders, switch tracks, icons that carry meaning, focus rings) ≥ 3:1 against adjacent colour. — Apple gives no number · fallback WCAG 2.2 SC 1.4.11 Non-text Contrast · measure: icon `fill/stroke` and input border vs background ratio ≥ 3.
- **G10** Semantic colour roles only: primary/secondary/tertiary label for text, grouped backgrounds for grouped lists; no separator colour used as text. — color: "don’t use the [separator] color as a text color, or [secondarylabel] color as a background color." · measure: CSS scan — text `color` resolves only to `--g-label*` tokens; grouped screens use `--g-bg-grouped*`.
- **G12** Grouped screens: page = systemGroupedBackground, group = secondarySystemGroupedBackground. — color: "use the grouped background colors ([systemGroupedBackground], [secondarySystemGroupedBackground], and [tertiarySystemGroupedBackground]) when you have a grouped table view" · measure: page bg ≠ group bg, and both equal the two grouped tokens per scheme.
- **G13** Resting (top-of-screen) state keeps full legibility under the glass bars. — color: "make sure its default or resting state — like the top of a screen of scrollable content — maintains clear legibility." · measure: at scrollY 0 no content text box intersects a bar rect.
- **G14** Every custom colour has light, dark and increased-contrast values (`prefers-contrast: more`). — color: "If you define a custom color, make sure to supply light and dark variants, and an increased contrast option for each variant" · measure: CSS scan — each `--g-*` colour token defined under `:root`, dark block, and `@media (prefers-contrast: more)`.

## 3. Spacing scale and layout (L)

- **L1** No horizontal page scroll at 320–1440 px widths; only an explicit carousel scrolls on x. — Apple gives no number · fallback WCAG 2.2 SC 1.4.10 Reflow (320 CSS px) · measure: at widths 320, 390, 768, 1024, 1440 `document.scrollingElement.scrollWidth ≤ innerWidth`.
- **L2** Side gutter 16 px on phone, 20 px ≥ 768 px; identical on every screen. — layout: "respecting system-defined safe areas, margins, and guides (where available)" · Apple gives no number · Nadi token (`--g-screen-gutter`) · measure: first content box `left` = 16 (phone) on every route.
- **L3** Content and controls never sit under the status bar, notch or home indicator (`viewport-fit=cover` + `env(safe-area-inset-*)`). — layout: "Respecting the safe area is essential to make sure system UI and hardware features like the Dynamic Island don’t obstruct content and controls." · measure: meta viewport contains `viewport-fit=cover`; every `position:fixed` top/bottom element's padding/inset string contains `safe-area-inset` (CSS scan); with a forced 47/34 px inset override, no control rect enters the inset band.
- **L3b** Full-screen backgrounds extend under bars and safe areas (no white band at top/bottom). — layout: "For full-screen background content, be sure to extend it underneath sidebars, toolbars, and tab bars to fit the entire screen or window." · measure: `html,body` backgroundColor = page token; screenshot row 0 and last row match page colour.
- **L4** Every tap target ≥ 44 × 44 px (hit region, incl. padding/pseudo). — buttons: "a button needs a hit region of at least 44x44 pt" · measure: for all `button,a,[role=button],input,select,[tabindex]`, `getBoundingClientRect()` ≥ 44 in both axes (or an `::after` hit box ≥ 44).
- **L4b** Absolute floor 28 × 28 visible for dense inline controls, still with a 44 hit region. — accessibility: "iOS, iPadOS | 44x44 pt | 28x28 pt" (default | minimum) · fallback WCAG 2.2 SC 2.5.8 (24 × 24) · measure: no interactive rect < 28 in either axis.
- **L5** Gap between adjacent bordered controls ≥ 12 px; around borderless controls ≥ 24 px (or their hit regions don't overlap). — accessibility: "it works well to add about 12 points of padding around elements that include a bezel. For elements without a bezel, about 24 points of padding works well around the element’s visible edges." · measure: pairwise rect distance between sibling controls ≥ 12 (bezel) / hit boxes non-overlapping.
- **L6** Most important item is top-leading: primary figure/action is the first content element in DOM and on screen. — layout: "place the most important items near the top and leading side of the window or display." · measure: page's `[data-primary]` has min `top` among content blocks.
- **L10** Spacing scale: every margin/padding/gap ∈ {0, 2, 4, 8, 12, 16, 20, 24, 32, 35, 44, 48} px (hairlines 0.5/1 px exempt). — Apple gives no number (tvOS only: "Use consistent spacing.") · Nadi token (4-pt scale + 35 group gap) · measure: walk elements, every computed `margin*`, `padding*`, `gap`, `rowGap`, `columnGap` value ∈ scale.
- **L11** Same element type = same spacing everywhere: `.g-group` gap 35 px, row padding 12/16, stack sm/md/lg 8/12/16. — layout: "Group related items to clearly express related information or functions." · measure: distinct values of group-to-group gap across all routes = 1; distinct row paddings = 1.
- **L12** Space inside a group < space between groups (proximity). — layout: "use negative space, container shapes, or separator lines to show which elements are related and which are unrelated." · measure: within a group max inter-row gap < min inter-group gap.
- **L13** Evenly spaced stacked fields with consistent widths. — text-fields: "Evenly space multiple text fields." · measure: vertical gaps between consecutive fields in a form have spread ≤ 1 px; field widths in a group equal.
- **L7** Nested corners concentric: inner radius = outer radius − inset; capsules radius = height/2. — toolbars: "If you need to create a custom component, ensure that its corner radius is also concentric with the bar’s corners." · measure: for child with rounded bg inside rounded parent: `|rChild − (rParent − inset)| ≤ 1`.
- **L14** Radii only from the set {8, 12, 16, 20, 26, 28, 32, h/2}. — Apple gives no number · Nadi token (`--g-radius-*`) · measure: every computed `borderRadius` ∈ set.
- **L15** Nothing overlaps: no two visible text boxes intersect at any width or text size. — layout: "table rows or other containers may need to grow in height so that text isn’t cropped or doesn’t overlap other content" · measure: pairwise text-rect intersection area = 0 at 100 % and 200 % text.

## 4. Alignment — vertical and horizontal (A, new)

- **A1** Leading edges align: inside a group, every row title's left edge is equal (±0.5 px); icon rows align titles to one column. — layout: "Align elements to make them easier to scan, and use indentation to convey hierarchy." · measure: per `.g-group`, set of `.g-row__title` `left` values has spread ≤ 0.5.
- **A2** Group headers/footers align with the row text they label (same left as row title, not the group edge). — layout: "People assume that aligned items are related to each other, and conversely, they perceive indented items as subordinate to the item they follow." · measure: header `left` = first row title `left` ±0.5 (inset list style).
- **A3** Trailing values/accessories right-align to one edge per group (±0.5 px). — layout: "Alignment makes an app look neat and organized, and can help people track content while scrolling or moving their eyes." · measure: per group, `right` of `.g-row__value`/chevron spread ≤ 0.5.
- **A4** One text alignment per list: all items start-aligned (end-aligned in RTL). — right-to-left: "Use a consistent alignment for all text items in a list." · measure: all row text `textAlign` ∈ {start, left} and equal within a list.
- **A5** Single-line row content is vertically centred: |row centre − text centre| ≤ 1 px; icon centre = title centre ±1 px. — Apple gives no number · Nadi token · measure: for each single-line row, `(rect.top+rect.bottom)/2` of title vs row ≤ 1.
- **A6** Two-line rows: title and subtitle share one left edge; the block is centred against the leading icon (±1 px). — layout: "Align elements to make them easier to scan" · Nadi token for the ±1 · measure: title.left = subtitle.left; block centre vs icon centre ≤ 1.
- **A7** Icons sit on the text's optical line: icon box centre = text x-height centre ±1 px; icon size 16/20/24 from `--g-icon-*`. — sf-symbols: "Each symbol is also available in three scales: small, medium (the default), and large. The scales are defined relative to the cap height of the San Francisco system font." · measure: inline svg rect centre vs adjacent text line box centre ≤ 1.
- **A8** Numbers that are compared in a column use tabular figures and right-align. — Apple gives no number · Nadi token · measure: elements with `data-num` in lists have `fontVariantNumeric` containing `tabular-nums` and `textAlign: right|end`.
- **A9** Buttons in a row share height and baseline; button label centred both axes (±1 px). — buttons: "Use style — not size — to visually distinguish the preferred choice among multiple options." · measure: sibling buttons have equal `height`; label centre vs button centre ≤ 1 both axes.
- **A10** Bar title optically centred on the screen, not between the bar buttons. — Apple gives no number · Nadi token (iOS navigation bar behaviour) · measure: bar title centre x = `innerWidth/2` ±1.
- **A11** Horizontally scrolled partial content shows a peek at the trailing edge so scrollability is visible. — scroll-views: "displaying partial content at the edge of a view indicates that there’s more content in that direction." · measure: carousel `scrollWidth > clientWidth` ⇒ last visible child cut by the container edge (8–40 px visible).

## 5. Lists and default sort order (R, Q)

- **R1** Content lists are inset grouped lists; separators inset to the text start, none after the last row. — lists-and-tables: "the grouped style uses headers, footers, and additional space to separate groups of data" · measure: separator `left` = row title `left`; last row has no bottom border.
- **R3** Rows that navigate show a chevron; rows that act or toggle don't. — lists-and-tables: "If you need to let people drill into a list or table row’s subviews, use a disclosure indicator accessory control." · measure: row with `href`/router-link ⇔ has `.g-chevron`.
- **R4** Group header/footer: 13/18 regular, secondary label, sentence case. — lists-and-tables: "If you don’t include a column heading in a single-column table view, use a label or a header to help people understand the context." · measure: `.g-group__header` fontSize 13, color = secondary label token.
- **R5** Row min height 44 px; rows grow with content, never clip. — layout: "table rows with a single line of text by default might need to grow vertically to accommodate multiple lines of text." · measure: every row `height ≥ 44` and `scrollHeight ≤ clientHeight`.
- **R6** Long lists: 5 items then "See all"; older items folded by month; no endless scroll on find/check tasks. — lists-and-tables (watchOS section): "You can help make a long list more manageable by listing the most relevant items and providing a way for people to view more." · fallback NN/g "Infinite Scrolling Is Not for Every Website" (nngroup.com/articles/infinite-scrolling/) · measure: first render list child count ≤ 5 (+ a See-all row) on summary screens.
- **R7** Empty list shows one line of what is true + an action button when one exists; never blank. — writing: "An empty screen can be daunting if it isn’t obvious what to do next, so guide people on actions they can take, and give them a button or link to do so if possible." · measure: with API stubbed to `[]`, container has text length > 0 and (if action defined) a button.
- **R9** Row text short enough to avoid wrapping at default size; long text moves to the detail view. — lists-and-tables: "Keep item text succinct so row content is comfortable to read." · measure: row title `lineCount` = 1 at 390 px default text (warn).
- **R10** Selecting from an option list shows a checkmark on the chosen row; navigation rows keep the selected path highlighted on desktop. — lists-and-tables: "a table that lists options often highlights a row only briefly before adding an image — such as a checkmark — indicating that the item is selected." · measure: after tap, chosen row has `[aria-checked=true]` + checkmark svg; others none.
- **R11** No same-orientation nested scrollers (no vertical scroll box inside the vertical page). — scroll-views: "Avoid putting a scroll view inside another scroll view with the same orientation." · measure: no element other than the page scroller with `overflowY ∈ {auto,scroll}` and `scrollHeight > clientHeight`.
- **Q1** Every list has a declared default order, shown or implied by the group header (e.g. "This month", "Waiting for you"). — Apple gives no number (only macOS column sort) · Nadi token · measure: every list container has `data-sort` attribute; test fails if missing.
- **Q2** Time-based feeds (requests, check-ins, announcements, notifications): newest first by event time; ties broken by creation time, then name. — Apple gives no number · Nadi token · measure: read `data-ts` of rows, assert non-increasing.
- **Q3** Work queues (approvals waiting on you): oldest waiting first (longest wait at top), urgent/overdue group above. — Apple gives no number · Nadi token · measure: within "Waiting" group `data-ts` non-decreasing; overdue group precedes.
- **Q4** Upcoming items (shifts, leave, holidays): soonest first; past items folded below by month. — Apple gives no number · Nadi token · measure: future rows `data-ts` non-decreasing; past rows in a collapsed group.
- **Q5** People and type pickers: alphabetical by display name (locale collation `Intl.Collator`), recently used group on top when present. — Apple gives no number · Nadi token · measure: row names equal `[...names].sort(new Intl.Collator().compare)`.
- **Q6** Sort order is stable: same data renders the same order on reload and on desktop and phone. — layout: "Keep functionality the same as size classes change" · measure: row id sequence identical at 390 px and 1280 px and across two reloads.
- **Q7** Where users can change the sort, re-choosing the active key reverses it and the choice persists per list. — lists-and-tables (macOS): "If people click the heading of a column that’s already sorted, re-sort the data in the opposite direction." · measure: toggle twice ⇒ order reversed; reload ⇒ order kept.

## 6. Controls and forms (K)

- **K1** One look per control type: same height, radius, padding, font across screens. — toolbars: "Keep consistent groupings and placement across platforms." · measure: per control class, distinct (`height`,`borderRadius`,`fontSize`) tuples = 1.
- **K2** Forms are grouped lists: fields are rows in groups, labels leading, values trailing. — lists-and-tables: "iOS Settings uses a hierarchy of lists to help people choose options" · measure: every `input,select,textarea` has a `.g-row` ancestor inside `.g-group`.
- **K3** Picker values show names, never IDs or emails. — writing: "Choose simple, plain language and write with accessibility and localization in mind, avoiding jargon" · measure: no visible text matching `/^[A-Z]{2,}-\d|@[\w.-]+\.\w+|HR-EMP-/`.
- **K5** Prefer choice over typing: fixed value sets use a menu/picker, not a free text field. — entering-data: "When possible, offer choices instead of requiring text entry." · measure: fields with a known option set render `select`/menu button, not `input[type=text]`.
- **K6** Sensible defaults pre-filled (today, own name, usual shift). — entering-data: "You can also prefill fields with reasonable default values, which can minimize decision making and speed data entry." · measure: new-request forms: date field `value` non-empty on open.
- **K7** Field label stays visible while typing (placeholder is never the only label). — text-fields: "Because placeholder text disappears when people start typing, it can also be useful to include a separate label describing the field to remind people of its purpose." · measure: every input has `<label for>` or `aria-labelledby` pointing to visible text.
- **K8** Text fields with content show a trailing clear (×) button. — text-fields: "Display a Clear button in the trailing end of a text field to help people erase their input." · measure: typed search/text input shows a `[aria-label=Clear]` button ≥ 44 px at its trailing end.
- **K9** Continue/Send is disabled (or explains) until required data is present. — entering-data: "make the button available only after people enter the data you require." · measure: empty required form ⇒ primary `disabled` or `aria-disabled=true`.
- **K10** Validate on field exit (format) and inline, next to the field. — entering-data: "When you verify values as soon as people enter them — and provide feedback as soon as you detect a problem — you give them the opportunity to correct errors right away." · fallback WCAG 2.2 SC 3.3.1 · measure: invalid value + blur ⇒ `aria-invalid=true` and a message element within 8 px below the field.

## 7. Keyboard safety (K2x, new; P4/P6 kept)

- **P4** Inputs ≥ 16 px so iOS never zooms on focus; no pinch-zoom lock (`user-scalable` not `no`). — Apple gives no number · Nadi token (WebKit behaviour) · fallback WCAG 2.2 SC 1.4.4 · measure: every `input,select,textarea` fontSize ≥ 16; viewport meta has no `user-scalable=no`/`maximum-scale=1`.
- **P6** Right keyboard per field: `inputmode="decimal"` for hours/money, `numeric` for counts, `email`, `tel`, `search`. — virtual-keyboards: "Choose a keyboard that matches the type of content people are editing." · measure: fields tagged `data-kind=money|hours` have `inputmode=decimal`.
- **K21** Focused field is fully visible above the keyboard (not covered by keyboard, bars or sheet footer). — virtual-keyboards: "Using the layout guide also helps you keep important parts of your interface visible while the virtual keyboard is onscreen." · fallback WCAG 2.2 SC 2.4.11 Focus Not Obscured · measure: simulate keyboard with viewport 390 × 508 (Nadi token: 336 px keyboard) or `visualViewport` resize; focus each field; `rect.bottom ≤ visualViewport.height − 8` and `rect.top ≥ bar bottom`.
- **K22** The primary action stays reachable while the keyboard is up (sticky above keyboard or reachable by one scroll). — virtual-keyboards: "Use the keyboard layout guide to make the keyboard feel like an integrated part of your interface." · measure: in the 390 × 508 simulation, primary button is within the visual viewport after focusing the last field.
- **K23** Return key moves to the next field; last field's Return submits (`enterkeyhint="next"/"send"/"search"/"done"`). — virtual-keyboards: "Consider customizing the Return key type if it helps clarify the text-entry experience." · measure: every non-last input has `enterkeyhint=next`; last has `send|done|search`.
- **K24** Tab/Next order follows visual order (top→bottom, leading→trailing). — text-fields: "When tabbing between fields, move focus in a logical sequence." · fallback WCAG 2.2 SC 2.4.3 · measure: press Tab through form; focused element `top` sequence non-decreasing.
- **K25** Use `interactive-widget=resizes-content` (or `visualViewport` handling) so fixed footers lift with the keyboard, and no layout jump > 0 on keyboard close. — virtual-keyboards: "Use the keyboard layout guide and standard padding to ensure the system positions your controls as expected within the view." · measure: viewport meta contains `interactive-widget`; after blur, `scrollY` returns and CLS delta = 0.
- **K26** Input accessory bars above the keyboard only hold controls for the current field and use glass like other bars. — virtual-keyboards: "If your app offers custom controls that augment the keyboard, make sure they’re relevant to the current task." · measure: accessory bar exists only while an input is focused.
- **K27** Correct autofill hints on identity fields (`autocomplete="username|current-password|one-time-code"`); passwords never pre-filled. — entering-data: "Never prepopulate a password field." · measure: `input[type=password]` value empty on load and has `autocomplete`.
- **K28** Full keyboard use on desktop: every control reachable by Tab with a visible focus ring (≥ 2 px, ≥ 3:1). — accessibility: "Let people use the keyboard alone to navigate and interact with your app." · fallback WCAG 2.2 SC 2.4.7 · measure: Tab through page; each focused element has non-`none` outline/box-shadow.

## 8. Buttons (B)

- **B1** One prominent (filled) button per screen; two is the hard ceiling. — buttons: "Keep the number of prominent buttons to one or two per view." · measure: count `.g-btn--primary` visible ≤ 1 (warn at 2, fail at 3).
- **B2** Secondary/tertiary differ by style, not size: all buttons in a set share height. — buttons: "placing two buttons of different sizes near each other can make the interface look confusing and inconsistent." · measure: sibling buttons equal height.
- **B3** Destructive action never primary; it uses system red. — buttons: "Don’t assign the primary role to a button that performs a destructive action, even if that action is the most likely choice." · measure: `[data-destructive]` never has primary class; color = red token.
- **B4** Labels are verbs that name the result; no "Submit", "OK" (except info alerts), "Click here". — writing: "When labeling buttons and links, it’s almost always best to use a verb." · measure: button text not in {Submit, OK, Yes, No, Click here} outside info alerts.
- **B6** Every custom button has a pressed state (visible within 100 ms). — buttons: "Always include a press state for a custom button." · measure: on `pointerdown` computed `opacity`/`transform`/`background` differs within 100 ms.
- **B6b** Slow action = spinner inside the button with a progress label ("Sending…"), button keeps its width. — buttons: "Configure a button to display an activity indicator when you need to provide feedback about an action that doesn’t instantly complete." · measure: throttle API 2 s; button shows `[role=progressbar]`/spinner, width change ≤ 1 px, no second submit on double tap.
- **B7** Bar buttons: borderless symbols; no text button right next to a symbol; ≤ 3 groups. — toolbars: "Minimize the number of groups." and "In general, aim for a maximum of three." · measure: bar item groups ≤ 3; no text button adjacent to icon button without ≥ 8 px gap.
- **B8** Back = chevron symbol, Close = × symbol, never the words. — toolbars: "Prefer the standard symbols for each, and don’t use a text label that says Back or Close." · measure: back/close buttons have svg + `aria-label`, no visible text "Back"/"Close".
- **B10** One primary toolbar action, on the trailing side. — toolbars: "Only specify one primary action, and put it on the trailing side of the toolbar." · measure: prominent bar item is the last child of the trailing group.

## 9. Navigation, desktop and sidebar (N, L9)

- **N1** Tab bar: ≤ 5 tabs, single-word labels always shown, navigation only (no action tabs). — tab-bars: "Use a tab bar to support navigation, not to provide actions." and "Use single words whenever possible." · measure: tab count ≤ 5; each label one word; each tab is a link.
- **N2** Tab bar visible on every section screen; only modals cover it. — tab-bars: "Make sure the tab bar is visible when people navigate to different sections of your app." · measure: on every non-modal route the tab bar rect is in viewport.
- **N6** Tabs are never disabled or hidden; an empty section explains why. — tab-bars: "Don’t disable or hide tab bar buttons, even when their content is unavailable." · measure: tab set identical for every persona.
- **N7** Tab badge (red, number) only for items needing action. — tab-bars: "Reserve badges for critical information so you don’t dilute their impact and meaning." · measure: badge count = count of actionable items from the API.
- **N8** Tab switch preserves each section's navigation and scroll state. — tab-bars: "They also let people quickly switch between sections of the view while preserving the current navigation state within each section." · measure: scroll a tab, switch away and back ⇒ same route and `scrollY` ±2.
- **L9** Desktop (≥ 1024 px): sidebar + one content column, same components and same features as phone. — layout: "Don’t change your app’s functionality based on the space it occupies." · measure: set of reachable routes/actions at 390 px = set at 1280 px.
- **L9b** Choose layout by available width (media queries on width), never by user-agent/device. — layout: "Determine layout based on size classes, not device type or orientation." · measure: code scan — no `navigator.userAgent`/`platform` branch drives layout; resizing a desktop window to 390 gives the phone layout.
- **N5** Sidebar lists the same destinations in the same order as the tab bar, with the same symbols. — layout: "Consider taking advantage of larger spaces to switch from a [tab-bars] to a [sidebars]" · measure: sidebar item labels sequence = tab labels sequence (+ extra items only after).
- **N9** Sidebar shown by default on desktop, max two levels, short group labels. — sidebars: "Avoid hiding the sidebar by default to ensure that it remains discoverable." and "In general, show no more than two levels of hierarchy in a sidebar." · measure: at 1280 px sidebar visible on load; nesting depth ≤ 2.
- **N10** Wide content centred in a readable column (≤ 720 px) with the grouped background filling the rest; no stretched rows across 1440 px. — layout: "restrict the width of text for optimal readability" · Nadi token 720 · measure: at 1440 px `.g-group` width ≤ 720.
- **N11** Restore state on reopen: last tab, route and scroll position. — launching: "Restore the previous state when your app restarts so people can continue where they left off." · measure: navigate + scroll, reload ⇒ same route and scroll ±20 px.
- **N3** Pushed screen bar: back chevron leading, inline title, ≤ 1 primary trailing. — toolbars: "Leading edge. Elements that let people return to the previous document and show or hide a sidebar appear at the far leading edge, followed by the view title." · measure: back button is first child of the bar.

## 10. Sheets, alerts, feedback (S)

- **S1** Sheets hold a short task; long or multistep flows are pushed screens. — sheets: "For complex or prolonged user flows, consider alternatives to sheets." · measure: sheet content ≤ 1 screen of fields (≤ 6 rows) else flagged.
- **S2** Sheet bar: Cancel/× leading, Done/verb trailing; never Cancel + Done + Back together. — sheets: "for sheets with a single view, the Cancel button belongs on the leading edge of the top toolbar. When present, the Done button belongs on the trailing edge." and "Avoid showing all three buttons — Cancel, Done, and Back — together." · measure: sheet header first child = close, last = confirm; never 3 buttons.
- **S3** Resizable sheets have a grabber; swipe down dismisses; unsaved edits ask via action sheet. — sheets: "If people have unsaved changes in the sheet when they begin swiping to dismiss it, use an action sheet to let them confirm their action." · measure: type in sheet, drag down ⇒ action sheet appears, sheet stays.
- **S4** One sheet at a time. — sheets: "Display only one sheet at a time from the main interface." · measure: count open `[role=dialog]` ≤ 1.
- **S6** Every swipe gesture has a visible button alternative. — accessibility: "if you use a swipe gesture to dismiss a view, also make a button available so people can tap or use an assistive device." · measure: every swipe-dismiss surface also has a close button.
- **S7** Alert: title says what happened (≤ 2 lines, never "Error"), ≤ 3 buttons, "Cancel" named Cancel, destructive only for unintended loss. — alerts: "Avoid writing a title that doesn’t convey useful information — like “Error” or “Error 329347 occurred” — but also avoid overly long titles that wrap to more than two lines." · measure: alert title ≠ /error/i alone, height ≤ 2 lines, buttons ≤ 3.
- **S8** No alert at launch; no alert for information only. — alerts: "Avoid showing an alert when your app starts." · measure: fresh load of every route ⇒ no `[role=alertdialog]` within 3 s.
- **S9** No time-boxed UI for anything the person must read or act on; toasts that carry an action or error stay until dismissed; info toasts ≥ 5 s (Nadi token). — accessibility: "Views and controls that auto-dismiss on a timer can be problematic for people who need longer to process information" · fallback WCAG 2.2 SC 2.2.1 Timing Adjustable · measure: error/undo toast still present after 10 s.
- **S10** Status feedback sits next to what it describes and is announced (`role=status`/`aria-live`). — feedback: "When status feedback is available near the items it describes, people get important information without having to take action or leave their current context." · fallback WCAG 2.2 SC 4.1.3 Status Messages · measure: after save, a `[role=status]` element within the same group has text.
- **S11** Confirm success only for significant actions (send, approve, check-in); routine saves are silent. — feedback: "It’s generally best to reserve this type of confirmation for activities that are sufficiently important" · measure: toggling a setting shows no toast; submitting a request shows one.
- **S12** Warn before unexpected irreversible loss only; undoable deletes don't alert. — feedback: "Warn people when they initiate a task that can cause data loss that’s unexpected and irreversible." · measure: undoable actions show Undo, not an alert.

## 11. Offline and error states with retry (O, new)

- **O1** Offline never shows a blank screen: last loaded data renders with a quiet "Offline — showing saved data" line + time of last update. — alerts: "you could show cached or placeholder data and a nonintrusive label that describes the problem." · measure: load route, `context.setOffline(true)`, reload ⇒ list rows > 0 and a `[role=status]` containing "Offline".
- **O2** Offline state is a banner/label, never a modal alert. — alerts: "If your app detects a problem at startup, like no network connection, consider alternative ways to let people know." · measure: offline reload ⇒ zero `[role=alertdialog]`.
- **O3** Every failed load shows: what failed (plain words), why if known, and a Retry button ≥ 44 px in the place the content would be. — writing: "When an error message is necessary, display it as close to the problem as possible, avoid blame, and be clear about what someone can do to fix it." · measure: stub API 500 ⇒ container shows text + `button` named /try again|retry/i, height ≥ 44.
- **O4** Retry works without a page reload and restores the view in place (keeps scroll and form input). — progress-indicators: "If a process stalls for some reason, provide feedback that helps people understand the problem and what they can do about it." · measure: 500 then 200; tap Retry ⇒ rows render, `location.href` unchanged, typed input kept.
- **O5** Error copy: no "we", no "oops", no codes; "Couldn’t load your requests. Check your connection and try again." pattern. — writing: "Avoid using we altogether because it may be unclear who the “we” in question refers to." and "Interjections like “oops!” or “uh-oh” are typically unnecessary and can sound insincere." · measure: error text !~ /\b(we|oops|uh-oh|error \d+|exception)\b/i.
- **O6** Actions while offline: disable the send button with a reason, or queue and label "Will send when online"; never lose typed input. — feedback: "Show people when a command can’t be carried out and help them understand why." · measure: offline, fill form, tap send ⇒ input value preserved and a visible reason/queued label.
- **O7** Reconnect auto-refreshes stale data and removes the offline label within 2 s of `online`. — progress-indicators: "Don’t make people responsible for initiating every update." · Nadi token 2 s · measure: `setOffline(false)` ⇒ offline label gone and a fetch fired within 2 s.
- **O8** A partial failure fails small: one failed card shows its own retry; the rest of the screen renders. — feedback: "The most effective feedback tends to match the significance of the information to the way it’s delivered." · measure: stub one endpoint 500 ⇒ other groups render, only that group shows Retry.
- **O9** Server validation errors map to the field, not a generic banner. — writing: "Show errors right next to the field, and instruct people how to enter the information correctly, rather than scolding them for not following the rules." · fallback WCAG 2.2 SC 3.3.3 Error Suggestion · measure: 417 with field error ⇒ message under that field, `aria-describedby` set.
- **O10** Session expiry / 403 shows a plain next step (sign in again / ask HR) — never a raw status page. — feedback: "An opportunity to correct a mistake or problematic situation" · measure: stub 403 ⇒ visible text has no "403"/"Forbidden" and has a button.

## 12. Loading and skeletons (D, new; P7 kept)

- **D1** Show something immediately: route shell (bar + group outlines) paints before data; never a blank page. — loading: "If you make people wait for loading to complete before displaying anything, they can interpret the lack of content as a problem with your app or game." · measure: with API delayed 3 s, first paint contains the bar title and ≥ 1 placeholder within 300 ms of navigation.
- **D2** List/card loading = skeleton rows shaped like the real rows (same height ±2 px, same count up to 5). — loading: "consider showing placeholder text, graphics, or animations as content loads, replacing these elements as content becomes available." · fallback NN/g "Skeleton Screens 101" (nngroup.com/articles/skeleton-screens/) · measure: skeleton row height = loaded row height ±2; CLS on swap ≤ 0.01.
- **D3** No spinner for waits < 1 s; show the skeleton/spinner only after ~300 ms delay to avoid flash (Nadi token 300 ms). — Apple gives no number · fallback NN/g "Response Times: The 3 Important Limits" (nngroup.com/articles/response-times-3-important-limits/: 0.1 s / 1 s / 10 s) · measure: API 150 ms ⇒ no loading indicator ever in DOM; API 2 s ⇒ indicator appears after 300 ±50 ms.
- **D4** Waits > 10 s (uploads, exports, rebuilds) use a determinate bar with honest progress and a Cancel. — progress-indicators: "When possible, use a determinate progress indicator." and "If people can interrupt a process without causing negative side effects, include a Cancel button." · measure: upload shows `[role=progressbar][aria-valuenow]` increasing; Cancel button present.
- **D5** Progress advances evenly (no 90 % then stall). — progress-indicators: "Showing 90 percent completion in five seconds and the last 10 percent in 5 minutes can make people wonder if your app is still working and can even feel deceptive." · measure: sample `aria-valuenow` every 500 ms; no plateau > 5 s while the request is live.
- **D6** Indicators keep moving; a stall > 10 s turns into an explanation + retry (O3). — progress-indicators: "Keep progress indicators moving so people know something is continuing to happen." · measure: API hang 15 s ⇒ after ≤ 10 s an explanatory text + Retry appears.
- **D7** Never morph a spinner into a bar (or back). — progress-indicators: "Don’t switch from the circular style to the bar style." · measure: during one operation the indicator element type is constant.
- **D8** Loading labels say what is loading ("Getting your shifts"), never bare "Loading…". — progress-indicators: "Avoid vague terms like loading or authenticating because they seldom add value." · measure: visible text !~ /^loading\.*$/i.
- **D9** Loading indicators appear in one consistent place per surface (in-place skeleton for lists, in-button spinner for actions, top of sheet for sheet loads). — progress-indicators: "Display a progress indicator in a consistent location." · measure: across routes, list loading always renders inside the list container (not a centered page spinner).
- **D10** Loading is never shown as empty: the empty message renders only after a successful response with 0 items. — writing: "Remember that empty states are usually temporary, so don’t show crucial information that could then disappear." · measure: during pending fetch, empty-state text absent; after `[]`, present.
- **D11** Background refresh doesn't replace visible content with a skeleton (stale-while-revalidate); rows update in place. — loading: "Let people do other things in your app or game while they wait for content to load." · measure: second visit to a route shows real rows at first paint (no skeleton).
- **D12** Pull to refresh only on changing lists; its spinner has no instructional title. — progress-indicators: "If you do include a title, don’t use it to explain how to perform a refresh." · measure: refresh control text (if any) !~ /pull|release/i.
- **D13** Automatic freshness: data older than 5 min refreshes on focus/visibility (Nadi token 5 min). — progress-indicators: "Keep data fresh by updating it regularly." · measure: fake time +6 min, `visibilitychange` ⇒ fetch fired.
- **D14** Launch: the first screen looks like the launch screen (same background, no logo splash, no text). — launching: "Design a launch screen that’s nearly identical to the first screen of your app or game." · measure: manifest `background_color` = page bg token per scheme; no splash route.
- **D15** Images/avatars reserve space (width/height or aspect-ratio) and fall back to initials. — Apple gives no number · fallback web.dev CLS ≤ 0.1 · measure: every `img` has explicit size or aspect-ratio; broken URL ⇒ initials tile, same box.

## 13. Performance (F, new)

- **F1** Launch to usable first screen ≤ 2 s on a mid phone (cold, 4G), shell paint ≤ 1 s. — launching: "People want to start interacting with your app or game right away, and sometimes they don’t want to wait more than a couple of seconds." · measure: WebKit trace, 4× CPU + Fast-4G throttle: first route interactive ≤ 2000 ms.
- **F2** LCP ≤ 2.5 s at p75. — Apple gives no number · fallback web.dev Core Web Vitals (LCP ≤ 2.5 s) · measure: `PerformanceObserver('largest-contentful-paint')` value ≤ 2500.
- **F3** INP ≤ 200 ms: every tap handler responds (next paint) within 200 ms; pressed state within 100 ms. — Apple gives no number · fallback web.dev Core Web Vitals (INP ≤ 200 ms); NN/g 0.1 s limit · measure: `event` timing entries `duration` ≤ 200 for scripted taps on every primary control.
- **F4** CLS ≤ 0.1 per route (skeleton→content swap included); target 0.01 on list screens. — Apple gives no number · fallback web.dev Core Web Vitals (CLS ≤ 0.1) · measure: sum `layout-shift` entries (no recent input) ≤ 0.1.
- **F5** No long task > 50 ms during scroll; scroll stays at 60 fps (frame gap ≤ 16.7 ms p95). — motion: "maintaining a consistent frame rate of 30 to 60 fps typically results in a smooth, visually appealing experience." (games) · fallback web.dev long tasks 50 ms · measure: `longtask` observer during scripted scroll ⇒ 0 entries; rAF gap p95 ≤ 17 ms.
- **F6** Glass (`backdrop-filter`) only on bars/sheets: ≤ 4 blurred elements on screen at once. — layout: "Take advantage of the Liquid Glass material on all platforms that support it to provide a distinct appearance for your controls." · Nadi token 4 · measure: count visible elements with computed `backdropFilter ≠ none` ≤ 4.
- **F7** Initial JS for the first route ≤ 200 KB gzip; other routes lazy-loaded. — Apple gives no number · Nadi token · measure: sum transfer size of `script` resources before first interaction ≤ 200 KB.
- **F8** Long lists render at most ~50 rows at once (paged/folded per R6). — Apple gives no number · Nadi token · measure: row count in DOM ≤ 50 on any screen before "See all".
- **F9** Animations use only `transform`/`opacity`; no animated `backdrop-filter`/blur. — accessibility: "Avoiding animating into and out of blurs" · measure: CSS scan — `transition`/`@keyframes` properties ⊆ {transform, opacity, color, background-color}.
- **F10** Service worker serves the shell and last data offline (supports O1). — Apple gives no number · Nadi token · measure: offline reload returns 200 for `/` and the route JS.

## 14. Motion (M) — kept, two additions

- **M5** No motion on frequent interactions (row taps, toggles) beyond the press state. — motion: "In apps, generally avoid adding motion to UI interactions that occur frequently." · measure: row tap triggers no `animationstart` other than press feedback.
- **M6** Reduce Motion: slides → fades; no scale, parallax, blur animation; springs tightened. — accessibility: "Replacing transitions in x-, y-, and z-axes with fades to avoid motion" · measure: `reducedMotion: 'reduce'` ⇒ push transition animates only `opacity`.
- **M9** Animations never block input: a tap during a transition is handled (cancelable). — motion: "don’t make people wait for an animation to complete before they can do anything" · measure: tap back mid-push (at 100 ms) ⇒ navigation reverses, no ignored tap.
- **M10** Motion follows the gesture direction: what slides in from the bottom leaves to the bottom. — motion: "if someone reveals a view by sliding it down from the top, they don’t expect to dismiss the view by sliding it to the side." · measure: sheet open/close `transform` axis both Y.

## 15. Words and redundancy (W)

- **W1** Plain words, no ERP/jargon terms on screen (Posting date, Approver, Leave type, Document, Submit, Draft, Employee, Designation). — writing: "Choose simple, plain language and write with accessibility and localization in mind, avoiding jargon and gendered terminology." · measure: visible text has no word from the banned list.
- **W2** Address the person as "you"; never "we"; "your" sparingly. — inclusion: "It typically works well to use you and your to address people directly." and writing: "Use possessive pronouns sparingly." · measure: visible text !~ /\bwe\b|\bthe user\b/i.
- **W4** One term per concept across the app (glossary check). — writing: "Create a list of common terms, and reference that list to keep your language consistent." · measure: visible text contains no synonym from the glossary deny-list (leave, absence, OT claim…).
- **W6** Empty states: what's true + what to do. — writing: "Provide clear next steps on any blank screens." · measure: see R7.
- **W11** Remove redundant words: "Favorites", not "Your favorites"; no label repeating its group header; no title repeating the tab name on the same screen. — writing: "Check each word to be sure it needs to be there. If you can use fewer words, do so." · measure: no row label that starts with its group header text; bar title ≠ large title on the same screen.
- **W12** No redundant controls: one way to do each action per screen; no page indicator plus scroll indicator on one axis; no second button for the same result. — scroll-views: "don’t show the scrolling indicator on the same axis to avoid confusing people with redundant controls." · measure: per screen, no two enabled controls with the same accessible name and same action/route.
- **W13** No redundant alerts/explanations: don't explain what the buttons do; no help text that restates the label. — alerts: "Avoid explaining alert buttons." · measure: footer/hint text doesn't contain the button label verbatim.
- **W14** Settings footers describe what ON does only. — writing: "Describe what it does when turned on, and people can infer the opposite." · measure: switch rows' footer has no "when off".
- **W15** Link a setting instead of describing where it is. — writing: "If you need to direct someone to a setting, provide a direct link or button, rather than trying to describe its location." · measure: text !~ /go to .*> /i.
- **W16** Touch verbs: "tap", never "click". — writing: "not saying “click” for a touch device like iPhone or iPad where you mean “tap.”" · measure: visible text !~ /\bclick/i.

## 16. Native feel (P) — kept, with one addition

- **P1** No sideways drag, overscroll colour = page colour. — scroll-views: "If you build custom scrolling for a view, make sure your scroll indicators use the elastic behavior that people expect." · measure: `overscroll-behavior-x: none` on page; body bg = page token.
- **P2** No grey tap flash; custom pressed states instead. — buttons: "Without a press state, a button can feel unresponsive, making people wonder if it’s accepting their input." · measure: `-webkit-tap-highlight-color` alpha = 0 on interactive elements.
- **P5** Follow the system appearance (`prefers-color-scheme`); do not ship an in-app Light/Dark switch (see §17). — dark-mode: "Avoid offering an app-specific appearance setting." · measure: emulate dark ⇒ page uses dark tokens with no user setting; `<meta name="theme-color">` has light and dark `media` variants.
- **P9** Use system-flavoured controls (native date/time, select sheets) before custom ones. — dark-mode: "Use system views to draw text fields and text views." · measure: date fields are `input[type=date|time]` or the one `GDatePicker` component.

## 17. Where alpha6-standard is wrong or incomplete vs Apple's current text

1. **Type table weights are the *emphasized* weights, not Apple's defaults.** alpha6 lists Large Title/Title 1/Title 2 as "Bold", Title 3 "Semibold", Caption 2 "Semibold". Apple's default weight is Regular for all of these; Bold/Semibold is the emphasized variant. — typography: "Large Title | Regular | 34 | 41 | Bold" and "Caption 2 | Regular | 11 | 13 | Semibold". Using Bold is allowed, but the doc must say "emphasized", and Caption 2 tab labels at Semibold are a choice, not the spec.
2. **T2 claims Apple bans Heavy.** It does not — heavy is a listed emphasized weight. — typography: "The emphasized weights can be medium, semibold, bold, or heavy." Keep the 800/900 ban as a Nadi token and label it so.
3. **T5 tracking vs the tokens.** alpha6 says "−0.4 at 17"; Apple says −0.43 pt (−26/1000 em). The shipped token `--g-type-button-label-tracking: -0.01em` is −0.17 px at 17 px — less than half of Apple's value. — typography: "17 | -26 | -0.43".
4. **G9 contrast is incomplete.** Apple adds a 7:1 target for small text on custom colours and an Increase Contrast requirement; alpha6 has neither. — dark-mode: "strive for a contrast ratio of 7:1, especially in small text." and accessibility: "ensure it at least provides a higher contrast color scheme when the system setting Increase Contrast is turned on." Also note Apple's bold rule ("All | Bold | 3:1") is looser than WCAG (bold ≥ 14 pt); Nadi should use WCAG's 18.66 px bold threshold to stay safe.
5. **L4 omits the 28 × 28 minimum.** — accessibility: "iOS, iPadOS | 44x44 pt | 28x28 pt". 44 stays the rule; 28 is the hard floor for visible size.
6. **B1 is stricter than Apple, and cited as Apple.** Apple allows one or two prominent buttons per view (one in a toolbar). — buttons: "Keep the number of prominent buttons to one or two per view." Keep "one" as a Nadi token.
7. **S2 "always paired" overstates.** Apple pairs only when a Done button exists, and forbids three together. — sheets: "If you provide a Done button, always pair it with a Cancel button" and "Avoid showing all three buttons — Cancel, Done, and Back — together." A read-only sheet may have Close alone.
8. **P7 attributes "skeletons, not spinners" to Apple.** Apple says placeholders, and prefers determinate indicators; "skeleton" is NN/g's word. — loading: "consider showing placeholder text, graphics, or animations as content loads" and progress-indicators: "When possible, use a determinate progress indicator." alpha6 has no rule for determinate vs indeterminate, stalls, cancel, or style switching (added as D4–D7).
9. **P8 is incomplete.** Apple requires automatic refresh, not only pull-to-refresh. — progress-indicators: "Don’t make people responsible for initiating every update."
10. **No offline/error rules at all.** Apple's own pattern for "no network" is cached data + a quiet label, not an alert. — alerts: "you could show cached or placeholder data and a nonintrusive label that describes the problem." Added as O1–O10.
11. **Keyboard safety is one line (P6).** Apple asks for the keyboard layout guide and relevant accessory controls. — virtual-keyboards: "Using the layout guide also helps you keep important parts of your interface visible while the virtual keyboard is onscreen." Added as K21–K28.
12. **Appearance setting conflicts with Apple.** Nadi's Profile offers Light / Dark / Automatic (`frontend/src/views/Profile.vue:254`). — dark-mode: "Avoid offering an app-specific appearance setting." Needs an owner ruling: remove, or keep and log as a deliberate deviation.
13. **Time-boxed toasts are not covered.** — accessibility: "Minimize use of time-boxed interface elements." and "Prefer dismissing views with an explicit action." Added as S9.
14. **M6 Reduce Motion list is missing items that matter for glass.** — accessibility: "Avoiding animating into and out of blurs" and "Tightening animation springs to reduce bounce effects".
15. **Tab bar rules miss three Apple rules**: never disable/hide tabs, badges only for critical info, preserve per-tab state. — tab-bars: "Don’t disable or hide tab bar buttons, even when their content is unavailable." (added N6–N8).
16. **Desktop (L9/N5) misses Apple's size-class rules**: same functions at every width, layout by space not device, sidebar visible by default. — layout: "Determine layout based on size classes, not device type or orientation." and sidebars: "Avoid hiding the sidebar by default to ensure that it remains discoverable." Also Apple now says to try a tab bar first on iPad — sidebars: "Consider using a tab bar first." — so the sidebar is a Nadi choice for ≥ 1024 px.
17. **R6 "Show all" cites only NN/g**; Apple says the same thing (in the watchOS section). — lists-and-tables: "listing the most relevant items and providing a way for people to view more."
18. **No alignment rules.** alpha6 never states edge alignment, list alignment or indentation meaning. — layout: "Align elements to make them easier to scan, and use indentation to convey hierarchy." Added A1–A11.
19. **No sort-order rules.** Apple has none for iOS (macOS column-sort only); Q1–Q7 are Nadi tokens and must be labelled so.
20. **No Dynamic Type / 200 % rule.** — accessibility: "Ideally, give people the option to enlarge text by at least 200 percent" and typography: "Keep text truncation to a minimum as font size increases." Added T10–T12, T15.
21. **Layout page changed on 9 Sep 2026** ("Updated guidance to reflect current best practices"); its iOS section now reads "No additional considerations for iOS or iPadOS." Any alpha6 rule citing iOS-specific layout numbers from the older page (research in `/tmp/alpha6/`) should be re-checked against the current text.
22. **Launch/state restore missing.** — launching: "Restore the previous state when your app restarts so people can continue where they left off." and "Avoid including text on your launch screen" (added N11, D14).
