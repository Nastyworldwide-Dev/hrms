## 0. The two named symptoms — answered

### "Approver says approved, employee's PWA still says Open"

The database is right. `decide()` locks the row, sets the decision field and submits
in ONE save (`hrms/api/approval.py:246-300`). What the employee sees is stale for
three stacked reasons, and a fourth leaves the DB genuinely Open:

1. **Home "My Requests" refreshes only via one socket event.** `myLeaves`, `myOTRequests`
   etc. are module-scope resources fetched once at load; the only reload is
   `socket.on("hrms:refetch_resource")` (`frontend/src/data/leaves.js:20-39`,
   `socket.js:19-27`). No reload on navigation, resume, reconnect, or pull-to-refresh.
   A phone asleep at the moment of approval never hears about it. (A-C1, C-C1)
2. **The socket dies after 5 failed reconnects and nothing revives it.**
   `reconnectionAttempts: 5` (`socket.js:16`) → after ~20 s of bad signal every realtime
   feature is dead until a full reload. (A-H1)
3. **Last session's rows are painted first from IndexedDB.** 33 cached resources
   hydrate from `idb-keyval` before the network answers; if the fetch is held or fails
   the old "Open" stays. (C-H1)
4. **OT Request / Replacement Leave Claim / Comp Leave never publish a refetch at all.**
   Their controllers lack the `hrms.refetch_resource("hrms:my_*")` call the other four
   carry. (A-H2)

Why "Leave History" and the detail page show Approved while Home says Open:
`ListView`/`FormView` fetch on mount; Home does not. That matches the report exactly.

Second mechanism — **the DB really is still Open**: `decide()` re-runs every FILING
validator at DECISION time (Leave `validate_attendance`, balance, salary-processed,
Shift `validate_approver`, OT/AR mandatory attachment). These refuse **Reject** as well
as Approve. The approver reads a red toast on a phone for two seconds and remembers
tapping Approve. This is the exact class fixed for Attendance Request on 21 Sep
(bdbfd5005) and still open for the other six doctypes. (A-H3)

Not a cause: multi-level approval. There is none — no Workflow fixtures in the repo,
one approver per request, "Open" never means "one of two done". If the live site has a
Frappe Workflow on Leave Application, the PWA bypasses `decide()` entirely
(`approval.py:176-177`) and shows `workflow_state` — **owner check:** Desk → Workflow
list, filter Document Type = Leave Application. If one exists, tell me; it changes slice 1.

All three open the same screen (`fix_day.bundle.js`) and call the same endpoints

punches IS single-sourced (`ShiftType.get_attendance` → `calculate_working_hours`).

## 1. Critical — data integrity, authorization, wrong business state

### C1. Employee can write `status` on their own draft request (mass-assignment)
- **Problem.** Attendance Request, OT Request, Replacement Leave Claim, Comp Leave
  Request, Shift Request: `status` is permlevel 0, Employee has level-0 `write`,
  `read_only: 1` is a Desk-only hint. `frappe.client.set_value(<own draft>, "status",
  "Approved")` succeeds. Verified against the five JSON files in this session.
- **Location.** the five `*.json`; `hrms/api/approval.py:289, 325-339`.
- **Root cause.** The self-approval fence guards the decision PATH and the `employee`
  field, never the decision FIELD. Remote Checkin Request is the one doctype that
  guards it (`before_save`).
- **User impact.** (a) real approver gets "no longer awaiting a decision" — an employee
  can make their request un-rejectable; (b) `get_decision_actions` then offers the
  approver a single **Submit**, and `finalize` → `on_submit` pays out (attendance rows,
  banked OT, allocation) without the approver ever being asked.
- **Recommended change.** One shared `validate` hook for the five doctypes: refuse a
  decision-field change unless the writer is `_decision_access`-allowed. Invariant test
  that reads each `DECIDE_THEN_SUBMIT` JSON and fails if the field is Employee-writable
  at level 0 without the guard. (Alternative: permlevel 1 + guarded Property Setter
  patch — the memory note warns a Property Setter can shadow the JSON.)
- **Now.** `fix:`, regression test that sets status as the applicant.

### C2. Employee's Home never learns a decision except by one socket event
- **Problem / cause / impact.** §0 items 1–4. Realtime treated as a delivery guarantee.
- **Location.** `frontend/src/data/{leaves,overtime,attendance,claims}.js`,
  `socket.js:14-27`, `components/RequestPanel.vue:146-160`, `composables/realtime.js:43-52`,
  `views/Home.vue`; controllers `ot_request.py`, `replacement_leave_claim.py`,
  `compensatory_leave_request.py` (no `refetch_resource`).
- **Recommended change.** One cause, one slice: (1) reload `my_*` and `team_*` on
  RequestPanel mount, on socket `connect`, and on `visibilitychange → visible`;
  (2) `GPullRefresh` on Home; (3) drop `reconnectionAttempts` (default = forever) and
  `socket.connect()` on visible-when-disconnected; (4) `publish_update()` in the three
  controllers. Invariant test: every `hrms:my_*` key is reloaded by a non-socket path.
- **Now.** It is the reported symptom.

### C3. Fix Day's evidence predicate ignores `offshift`; rebuild stamps a shift onto an off-shift tap without clearing the flag
- **Problem.** `tap_state` returns "counted" for `offshift=1`; `_session_stamp` copies
  shift fields but not `offshift: 0` (`punch_stamp` does). Engine walls the tap.
- **Location.** `hrms/api/attendance_fix_day.py:167-187, 360-367, 1139-1151`;
  `shift_type.py:217-267`.
- **Root cause.** Two evidence predicates (Fix Day `counted` vs engine
  `counts_for_attendance`). No test uses `offshift=1`.
- **User impact.** HR sees a green OUT, presses Rebuild/Pair, gets "came back
  unchanged", day stays 0 h. The owner's "commonest broken day" shape.
- **Recommended change.** `counted()` = the engine's predicate (import it); one
  `session_stamp_from(tap)` used by both stampers; `day_plan` takes the engine's
  eligible list and its pairing (fixes B-H4 too). Invariant: every tap the screen
  calls "counted", the engine counts.
- **Now.** One file, small diff.

### C4. Fix Day's deadlock retry runs inside the HTTP request; HR's fix is silently discarded and logged "ok"
- **Problem.** `despite_deadlock` does a FULL `frappe.db.rollback()` (drops the tap
  writes, comments, lock) then re-marks on OLD evidence; `_finish` still writes the
  fix-log row and returns `ok: True`. Three failures → `deadlocked` → still `ok`.
- **Location.** `hrms/utils/day_remark.py:158-191`; `attendance_fix_day.py:1072-1103`.
- **Root cause.** Written for the RQ job (unit = whole transaction), reached inline
  through `remark_day(hr_asked=True)`.
- **User impact.** HR sees "fixed", log says fixed, day unchanged; nobody told.
- **Recommended change.** No rollback/retry when in a request — propagate, let the
  request roll back whole, HR sees an error. `_finish` never logs `deadlocked`/`held` as ok.
- **Now.** Regression test: stub the re-mark to raise 1213 once, assert Fix Day raises.
